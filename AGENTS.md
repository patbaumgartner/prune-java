# prune-java — agent instructions

Conservative Java dead-code analyzer (a `knip` for Java) shipped as a CLI, a language server, a Gradle plugin, and a Maven plugin on top of a shared core. See [README.md](README.md) for the philosophy, the detection rules, and each adapter's options.

**Detection is real and asserted.** `ConservativeUnusedCodeAnalyzer` reports the five `IssueType`s against the rules in the README, `SourceAutofixEngine` rewrites sources for the autofixable ones, and `SampleProjectFixtureTest` requires the report for each sample to equal its `expected-findings.txt` exactly. When you change a rule, the manifests and the README table change in the same commit — never edit a manifest to match whatever the analyzer happens to emit, and never loosen a guard to make a sample finding appear.

## Build and test

There are **two builds**, both wrapper-pinned with a distribution checksum, both fine on JDK 21 through 26.

```bash
./mvnw install                                   # prune-core, prune-cli, prune-lsp, prune-maven-plugin
./mvnw -pl prune-core test                       # one module
./mvnw -pl prune-core test -Dtest=ReportRendererTest
./mvnw install -Dinvoker.skip=true               # skip the Maven integration tests
java -jar prune-cli/target/prune-cli-0.1.0-SNAPSHOT.jar check --format=json --root=samples/maven-sample
java -jar prune-lsp/target/prune-lsp-0.1.0-SNAPSHOT.jar   # LSP over stdio; talks JSON-RPC, not a REPL

cd prune-gradle-plugin && ./gradlew build        # the Gradle plugin only
cd prune-gradle-plugin && ./gradlew publishToMavenLocal   # plugin + marker into ~/.m2, for builds outside TestKit
```

On newer JDKs Maven prints `sun.misc.Unsafe` lines to stderr that start with `WARNING`, and `-q` also hides the javac `[WARNING]` output you want. Filter instead: `./mvnw -B -ntp install 2>&1 | grep -v '^WARNING'`. Per-class test results are in `*/target/surefire-reports/*.txt`.

The `validate` phase and the Gradle `check` task fail on source that is not in Spring Java Format and on a pom that is not in sortpom's `custom_1` order with sorted properties. `./mvnw spring-javaformat:apply sortpom:sort` and `cd prune-gradle-plugin && ./gradlew format` put everything back into shape; run them before a build instead of hand-indenting. Java is tab-indented, `//` comments wrap at 90 columns and are never re-joined, so write them to fit. The formatter does not touch the *content* of text blocks, which is why the exact-position assertions in the tests survive it. The samples are formatted the same way by hand (`./mvnw -f samples/<name>/pom.xml io.spring.javaformat:spring-javaformat-maven-plugin:apply`, or the Gradle plugin through an init script) but carry no gate, since they must not reference this project.

`prune-core/src/test/java/.../source/ParserFuzzer.java` is the Jazzer target for all four hand-rolled parsers; it throws `IllegalStateException` on any broken invariant (spans inside the text, names at their offsets, dependencies anchored on real lines, baseline rejections carrying a location). `./mvnw -pl prune-core -Pfuzz test-compile exec:exec` fuzzes for `fuzz.seconds`; a crash lands next to the seeds in `ParserFuzzerInputs/` and `ParserFuzzerTest` replays every file there on each build. Keep crash inputs, fix the parser. The `jazzer-api` test dependency is the only artifact `prune-core` depends on besides JUnit, and only in test scope; the driver is confined to the profile.

Two automated-rewrite traps this repository has hit: OpenRewrite's `CodeCleanup` shortens `groovy.xml.XmlSlurper` to `XmlSlurper` in the Gradle scripts, which Groovy 4 does not resolve — keep it qualified; and `UpgradeSpringBoot_4_0` drops the explicit `UTF_8` from `Files.readString`/`writeString`, which is only correct on Java 18+ while this project targets 17 — never run Spring Boot migration recipes over the reactor.

To smoke-test the language server, pipe framed JSON-RPC messages into the jar and check the exit code; there is no interactive mode:

```bash
msg() { printf 'Content-Length: %d\r\n\r\n%s' "${#1}" "$1"; }
{ msg '{"jsonrpc":"2.0","id":1,"method":"shutdown"}'; msg '{"jsonrpc":"2.0","method":"exit"}'; } \
  | java -jar prune-lsp/target/prune-lsp-0.1.0-SNAPSHOT.jar; echo "exit=$?"   # expect 0; drop the shutdown message to expect 1
```

`prune-gradle-plugin` is a **separate Gradle build, not a Maven module** — a Gradle plugin needs the real Gradle API, which Maven cannot supply. It resolves `prune-core` from the local repository, so `./mvnw install` must run before it; `./mvnw verify` is not enough. After changing `prune-core`, re-run `./mvnw install` or the Gradle build compiles against a stale artifact.

`maven.compiler.release` in [pom.xml](pom.xml) compiles every module to **Java 17**. Do not use language features or APIs newer than 17.

`prune-gradle-plugin/gradle/wrapper/gradle-wrapper.jar` is re-included by a `!` rule in [.gitignore](.gitignore) that overrides the blanket `*.jar` exclusion. Keep that rule. Without it the wrapper jar silently stops being committed and the Gradle build breaks from a clean clone. The Maven wrapper is `only-script` and has no jar to protect.

## Module boundaries

`prune-core` depends on nothing. `prune-cli`, `prune-lsp`, `prune-gradle-plugin`, and `prune-maven-plugin` each depend only on `prune-core`, and never on each other. `prune-cli`, `prune-lsp`, and `prune-maven-plugin` consume it as a reactor module; `prune-gradle-plugin` consumes it as a published `com.patbaumgartner:prune-core` artifact.

Every integration module is a thin adapter: build an `AnalysisConfig`, call `UnusedCodeAnalyzer.analyze`, for `fix` hand the report to `new SourceAutofixEngine(root).fix(report)`, for `baseline` analyze `config.withoutBaseline()` and hand the issues to `Baseline.write`, then render or log the `AnalysisReport`. Anything reusable belongs in `prune-core`. Never let `prune-core` learn about Gradle, Maven, a CLI framework, or lsp4j.

Inside `prune-core` the pipeline is `config.BuildRoots` (decides how far above the analyzed root the build reaches: a Maven module belongs to the pom that lists it as a `<module>` or is its `<parent>` — read through `MavenPomParser.structure` — and a Gradle project to the nearest settings file unless it has its own; a pom that merely sits above a directory is not its build, which is why `samples/` with its own aggregator never climbs into the repository's root reactor) → `project.ProjectScanner` (walks the enclosing build, parses every `.java` file with `source.JavaSourceParser`, reads text resources under `src`, build files, and machine-read configuration outside `src` — `*.xml`, `*.properties`, `*.yml`, `*.yaml`, `*.MF` — but never prose formats, or a README naming a class would hide its finding, and never the configured baseline file, or it would hide every finding it lists; test sources are always read and flagged) → `analyzer.ReferenceIndex` (identifier, string-literal, and resource word indexes, split into main and test so `includeTestReferences` can drop the test half; build and configuration files feed the class-name index but not `DependencyUsage`, because a dependency's own declaration is not evidence it is used) → `ConservativeUnusedCodeAnalyzer` (decides what is a candidate and whether an identifier references it, then hands every unreferenced candidate to the `analyzer.Guard` pipeline) → `config.Baseline` (drops accepted findings) → `fix.SourceAutofixEngine` (re-locates each finding in the current text and plans whole-line deletions; `fix.ImportCleanup` drops imports a removal leaves unused). `dependency.MavenPomParser` and `dependency.GradleBuildParser` extract declarations; `dependency.DependencyUsage` decides usage with `dependency.KnownPackages` for exact package roots and coordinate tokens otherwise, and `DependencyUsage.keepReason` names why a declaration is never a candidate. `JavaSourceParser` is structural, not a full Java grammar: it finds top-level and nested types, members at depth one, spans, and modifiers (an annotation anywhere in a method's parameter list marks the member annotated), and marks anything it cannot follow as `opaque` so the analyzer skips it as a candidate while still counting its identifiers as references. Extend it rather than adding a parser dependency.

Every guard in `analyzer.BuiltInGuards` exists because of a concrete false-positive class, and each is one `Guard` with a stable `id()` that explanations print: `entry-point` (`main`, including the instance `main` a launcher accepts since Java 25), `annotation` (frameworks and reflection, on the member itself or on a parameter — CDI `@Observes`), `nested-type` (interface-nested and annotated-outer nested types: implicit visibility, framework pickup), `serialization` (hooks and `Serializable` fields), `native`, `annotated-owner` (JPA, Lombok, Jackson read private fields of annotated types), `reflective-serialization` (Gson, Jackson, JPA imports anywhere in the build keep every instance field, because a sibling module may serialize them), `javadoc` (documented public API of a library, `UNUSED_VISIBILITY` only), `module-info` (a `module-info.java` in the candidate's own module — the tree above its `src` — pins visibility; a sibling module's descriptor does not, `UNUSED_VISIBILITY` only), `literal` (string literals and resources: `Class.forName`, service loaders, Spring XML). The order is fixed and is the order explanations name them; `ConservativeUnusedCodeAnalyzer()` appends every `Guard` registered through `ServiceLoader` on `prune-core`'s class loader, sorted by id, and rejects duplicate ids. A guard can only keep a candidate, never add a finding, so a plug-in cannot make the analyzer less conservative. `Candidate` is sealed (`TypeCandidate`, `MemberCandidate`) and `AnalysisContext` is the only view of project-wide facts a guard gets; add to it rather than handing guards the `ReferenceIndex`. Removing a guard needs a test in `ConservativeUnusedCodeAnalyzerTest` proving the false positive it prevented no longer occurs, not just a passing sample. `KeptSymbol`s are only collected when `config.explain()` is set, so an unexplained run pays nothing for them.

In the Gradle plugin, never touch `getProject()` inside a `@TaskAction`. It breaks every consumer build that enables the configuration cache. Capture what the action needs into a task property at configuration time, as `PruneCheckTask.getProjectRoot()` does. [PruneGradlePluginTest.java](prune-gradle-plugin/src/test/java/com/patbaumgartner/prune/gradle/PruneGradlePluginTest.java) pins this with a TestKit build run under `--configuration-cache`. Every task type carries `@DisableCachingByDefault(because = ...)`: applying `maven-publish` switches `validatePlugins` to strict mode, which fails the build on a task type that does not say whether it is cacheable.

In the language server, **stdout is the wire**. `PruneLspApplication.main` redirects `System.out` to stderr before the launcher starts so a stray `println` cannot corrupt the JSON-RPC stream; keep that, and never hand the original stdout to anything but the launcher. `PruneLanguageServer` maps issues to diagnostics through `DiagnosticMapper`, clears diagnostics for URIs that dropped out of the latest report — publishing a new set without clearing the old leaves ghost squiggles in the editor — and keeps the last report so `QuickFixMapper` can turn a `codeAction` request into `SourceAutofixEngine` edits for the matching issue. lsp4j is the one external dependency an integration module carries, because it *is* the protocol; do not pull it into `prune-core` and do not hand-roll JSON-RPC. Two lsp4j 1.0.0 API traps: `Launcher.startListening()` returns a plain `Future`, not a `CompletableFuture`, so it cannot be combined with `CompletableFuture.anyOf`; and `Diagnostic.getMessage()` / `getCode()` return `Either`, so tests read them through `.getLeft()`.

## Sample projects

`samples/maven-sample` and `samples/gradle-sample` are plain-Java analyzer fixtures; `samples/spring-boot-sample`, `samples/quarkus-sample`, `samples/helidon-sample`, and `samples/micronaut-sample` are the framework fixtures that prove the guards on code the frameworks own. Each has deliberate dead code and one deliberately unused dependency — see [samples/README.md](samples/README.md). The four Maven samples are listed by `samples/pom.xml`, a pure aggregator (`com.example:samples`, parent of nothing) that lets one `mvn` invocation reach all of them; the root pom does not list it, so **no reactor builds them**, and the integration tests invoke prune goals and tasks directly rather than through a lifecycle phase, so the samples' dependencies are never resolved and the suite stays offline-safe. The aggregator also makes the four one reactor for the analyzer: references are collected from all of `samples/` when any Maven sample is analyzed. A sample's dead symbol must therefore be dead under the shared scan too — no other sample may import the package of its unused dependency, mention the name of a guarded type, or (for an instance field) import a reflective library. `SampleProjectFixtureTest` enforces this by analyzing every sample once inside `samples/` and once copied out on its own and requiring identical findings and explanations, and pins the aggregator's module list to the discovered Maven samples. Keep the samples free of any `com.patbaumgartner` reference and of any committed `prune-baseline.txt` (the same test fails on both): harness coupling belongs in `prune-maven-plugin/pom.xml` and in the Gradle functional test, not in the fixtures. Runs by hand against the Gradle samples go through [prune-java.init.gradle](prune-gradle-plugin/prune-java.init.gradle), which applies the plugin to the root project from outside the build — by class, because plugin-id lookup cannot see the init-script classpath — and resolves it from `~/.m2`, so `./gradlew publishToMavenLocal` must have run first.

Each sample's `expected-findings.txt` is the ground truth, and `SampleProjectFixtureTest` discovers every `samples/*/expected-findings.txt`, so a new sample needs a manifest and nothing else. Verdicts: `unused TYPE symbol` is reported exactly; `test-only TYPE symbol` is reported exactly, with an `is only referenced from tests` message, when `includeTestReferences` is off and not at all otherwise; `kept ANY symbol` is never reported and never explained (an identifier references it); `kept <guard-id> symbol` is never reported and is explained by exactly that guard. The explained set must equal the guard-naming `kept` rows, so every guard decision in a sample is written down. When you add a guarded symbol to a sample, its row names the guard; when you change a guard, the rows change in the same commit. The Gradle functional test and the Maven invoker IT drive the plain samples through the real plugins. The Maven IT runs with `prune.failOnIssues=false` because the sample is meant to have findings, and its `fix` and `baseline` goals rewrite the clone under `target/it`, never the sample itself.

Unit tests cannot catch goal- and task-invocation failures, which is why both plugins are also driven end to end. The Maven side runs through `maven-invoker-plugin` during `install`; that is what surfaced a mojo `@Parameter` declared as `String` that Maven could not inject from `${project.basedir}`. Logs land in `prune-maven-plugin/target/it/maven-sample/build.log`. The IT forks whichever Maven runs the build, so the wrapper legs in CI exercise the plugin under Maven 3.9 and the `maven4` job, which builds with a checksum-pinned Maven 4 download, exercises it under Maven 4. `maven.version` in the root pom is the plugin's floor (3.9.0) as well as the `maven-plugin-api` it compiles against, and Dependabot is told to leave it alone: bumping it to the newest patch locks every older Maven out of the plugin.

## Conventions

- **`prune-core` has zero runtime dependencies.** The JSON writer in [ReportRenderer.java](prune-core/src/main/java/com/patbaumgartner/prune/core/report/ReportRenderer.java) is hand-rolled deliberately — do not add Jackson or Gson. The Java lexer/parser and the pom/Gradle readers are hand-rolled for the same reason (the pom reader uses the JDK's SAX parser with external entities disabled), and guard discovery uses the JDK's `ServiceLoader`. Same for [PruneCliApplication.java](prune-cli/src/main/java/com/patbaumgartner/prune/cli/PruneCliApplication.java): argument parsing is hand-rolled, do not add picocli. `prune-lsp` depends on `org.eclipse.lsp4j` (pinned by `lsp4j.version` in the root pom) and nothing else beyond `prune-core`.
- Data is `record`s (`AnalysisConfig`, `AnalysisReport`, `AnalysisIssue`, `KeptSymbol`, `SourceLocation`, `FixAction`, `FixPlan`, `FixResult`, `TypeDeclaration`, `MemberDeclaration`, `DeclaredDependency`, `Candidate.TypeCandidate`, `Candidate.MemberCandidate`), behavior is `final class`es, extension points are `interface`s (`UnusedCodeAnalyzer`, `AutofixEngine`, `Guard`, `AnalysisContext`).
- Switch over `IssueType` / `OutputFormat` / `Severity` with exhaustive `switch` expressions and **no `default` branch**, so adding a constant breaks compilation at every site that must handle it.
- Almost no comments and no Javadoc in existing code. Match that: comment only what the code cannot show, and keep `//` comments within 90 columns because the formatter splits longer ones into stubs.
- New analysis behavior must stay conservative — a false positive that deletes live code is worse than a missed finding. Every rewrite goes through `FixAction` with the exact `original` text, `SourceAutofixEngine.apply` refuses to touch a file whose text no longer matches the plan, writes go through a sibling temp file and an atomic move, and a target whose real path leaves the root is never planned.
- The version lives once, in the root [pom.xml](pom.xml); `prune-gradle-plugin/build.gradle` reads it from there. Do not hard-code it in the Gradle build again.
- Releases are tag-driven: pushing `vX.Y.Z` runs [release.yml](.github/workflows/release.yml), which stages the reactor (`mvn deploy` to a local directory) and the Gradle plugin (`publishAllPublicationsToStagingRepository`), attests provenance, and hands both directories to JReleaser ([jreleaser.yml](jreleaser.yml)) for signing, Maven Central, and the GitHub release. `project.build.outputTimestamp` must be bumped with the version or the workflow refuses the tag; the `Reproducible build` CI job is what makes that timestamp mean something. Commit messages follow Conventional Commits because the changelog is generated from them. The procedure is in [CONTRIBUTING.md](CONTRIBUTING.md#releasing).
- Module POMs are flattened (`flatten-maven-plugin`, `oss` mode) on install and deploy, so the published `prune-core` POM has no parent and no `${...}` left in it; check `target/.flattened-pom.xml` when a change touches inherited metadata.
- [.github/dependabot.yml](.github/dependabot.yml) owns version updates for Maven, Gradle, and the SHA-pinned actions; [SECURITY.md](SECURITY.md) states the trust model users rely on. Keep both true when behavior changes.

## Contracts that tests lock in

Changing any of these is a breaking change; update the tests deliberately, not incidentally.

- **CLI exit codes**: `0` success (`check` clean, `fix` left nothing, `baseline` written), `1` `check` found issues or `fix` left issues that need a human, `2` usage error (unknown command, unknown option, unsupported `--format`, `--root` not a directory, empty or invalid `--exclude`, empty `--baseline`), `3` analysis or rewrite failure (including a malformed baseline file and a baseline that cannot be written).
- **Format defaults**: `--ci` implies `github` output, otherwise `terminal`; an explicit `--format` wins. `--root=<dir>` selects the project; the working directory is the default. `--exclude=<glob>` is repeatable and removes candidates without removing references. `--explain` adds kept symbols to the report; `--no-test-references` drops test sources from the reference set for `UNUSED_CLASS`/`UNUSED_METHOD`/`UNUSED_FIELD` (never for `UNUSED_VISIBILITY`); `--baseline=<file>` replaces `<root>/prune-baseline.txt`. The usage line is asserted verbatim in `PruneCliApplicationTest`.
- **Baseline file**: `TYPE symbol` per line, `#` comments, blank lines ignored; malformed lines and unknown types fail with `<file>:<line>: ...`. A missing file is an empty baseline everywhere. The `baseline` entry points analyze without the existing baseline and write `Baseline.render` (header comment plus sorted unique lines). Suppressed findings add ` N issue(s) suppressed by <root-relative file>.` to the summary and never reach `fix`.
- **Symbols and locations**: `AnalysisIssue.symbol` is `fully.qualified.Type`, `fully.qualified.Type.Nested`, `fully.qualified.Type#member`, or `groupId:artifactId`; `location` is `path[:line[:column]]` relative to the analyzed root with one-based positions, and issues are sorted by path, line, column, type, symbol. Class findings anchor at the type name, member findings at the member name, dependency findings at the `artifactId` line. `KeptSymbol` uses the same symbol and location forms and the same order.
- **Autofixable**: `UNUSED_METHOD`, single-declarator `UNUSED_FIELD`, `UNUSED_VISIBILITY`, and `UNUSED_DEPENDENCY` are autofixable; `UNUSED_CLASS` never is. `fix` reports `Applied N autofix(es) in M file(s); K issue(s) remain (conservative mode).` and lists only the remaining issues.
- **Plugin parameters**: Maven `prune.failOnIssues` (default `true`), `prune.format` (`terminal`), `prune.excludes` (comma-separated globs), `prune.baseline` (a `File`), `prune.testReferences` (`true`), `prune.explain` (`false`, `check` only), `prune.skip`, and all three goals skip `pom` packaging; Gradle `pruneCheck.ignoreFailures` (default `false`) plus `format`, `excludes`, `baseline` (`RegularFileProperty`, `@Internal` because the file may not exist), `testReferences`, `explain` on `pruneCheck`, the first four on `pruneFix`, and `excludes`/`baseline` (`@OutputFile`)/`testReferences` on `pruneBaseline`, which is never up to date. Both fail with `prune-java found N unused-code issue(s).`
- **Guard ids** are part of the output: `entry-point`, `annotation`, `nested-type`, `serialization`, `native`, `annotated-owner`, `reflective-serialization`, `javadoc`, `module-info`, `literal`, plus `dependency-scope`, `dependency-type`, `runtime-only`, `ambiguous-coordinates` for dependencies and `baseline` for suppressed findings. `GuardPipelineTest` pins the built-in order and the `ServiceLoader` hook through a test-classpath `META-INF/services` entry.
- **LSP diagnostics**: source `prune-java`, code = `IssueType.name()`, tag `Unnecessary`, severity mapped `INFO→Information`, `WARNING→Warning`, `ERROR→Error`. `AnalysisIssue.location` is parsed by `SourceLocation` as `path[:line[:column]]` (1-based, converted to 0-based); a bare path anchors at `0:0`. The server advertises save-only sync (`openClose=false`, `change=None`, `save=true`) plus a `quickfix` code-action provider, and re-analyzes on `didSave` and `didChangeWatchedFiles`. Process exit code is `0` after `shutdown` then `exit`, and `1` if `exit` arrives without a prior `shutdown`, as the LSP spec requires.
- **Output escaping**: issue `symbol`, `location`, and `message` originate from analyzed source, and so do `KeptSymbol` fields and guard ids from plug-ins, so every sink escapes for its own context. JSON goes through `escapeJson` (and always carries a `"kept":[...]` array, empty unless explanations were requested); the GitHub `file=` property goes through `escapeGithubProperty` (which additionally escapes `:` and `,`, or a crafted path can spoof annotation properties) while `line=`/`col=` come from the parsed `SourceLocation` integers; the GitHub message goes through `escapeGithubData` and kept symbols are never emitted as annotations; terminal output goes through `escapeControlCharacters`, or ANSI sequences from analyzed source can rewrite the report. Reusing the wrong helper reintroduces an injection.

Test conventions live in [.github/instructions/tests.instructions.md](.github/instructions/tests.instructions.md).
